# 판정과 보고

## 이슈 코멘트 머리말

한 줄로 결과·기기·빌드·서버를 먼저 쓴다.
```
🤖 **iOS 자동 테스트: PASS** · <모델>(<제품 ID>) · iOS <버전> · Development 빌드(<CL/커밋>) · <서버 환경> · <날짜>
```
결과 단어는 네 가지로만: **PASS / FAIL / 부분 확인(상태 유지) / 시험 불가(사유)**.

## 본문

- 무엇을 했는지 → 무엇을 봤는지(숫자·파일명·시각) → 기대값과 비교 순서로.
- 기대값을 서버 데이터에서 계산했다면 계산식과 원본 값을 같이(예: `본편 7,367,539,616B + 멤버 429,074,624B = 7.80GB, 화면 7.3GB`).
- 단위 규칙(10진 GB vs 2진 GiB)이 판정을 가르면 명시.
- 스크린샷은 필요한 영역만 잘라 붙인다. 비공개 저장소라면 이미지를 별도 브랜치에 커밋하고 `blob/<sha>/<path>?raw=true` 링크를 쓰면 읽기 권한이 있는 사람에게 렌더된다.
- 시험 중 만든 부수효과(파일 삭제, 설정 변경, 다른 빌드로 덮어쓰기)는 끝에 적는다.
- 시험하지 못한 것은 따로 한 줄: 무엇을, 왜 못 했는지.

## 상태 변경

보드 상태는 기준이 명확할 때만 바꾼다. 실버그 재현 → In Progress/Todo 유지 + 재현 절차, 기대와 일치 → Done 또는 다른 플랫폼 대기 상태. 기획 판단이 필요한 차이는 상태를 그대로 두고 질문으로 남긴다.

## 실버그를 찾았을 때

재현 절차(최소 단계), 관찰(로그 발췌·시각), 원인 단서(어느 계층에서 멈췄는지), 우회(앱 재실행/취소 후 재시도 등이 되는지)를 적는다. 수정은 담당자 확인 후.
